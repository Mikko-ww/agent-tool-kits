# GitHub 项目取证调研

搜索用户真正要解决的问题，而不是机械复用用户输入的词。先建立目标产品或方向的准确画像，再多路发现候选、**取证**，最后分别评价相似度、适合度和项目质量。

星数是采用度信号，不等于相似度或代码质量。`updatedAt`、最近提交和发布时间也不等于 Star 趋势。

与轻量选品的区别只有一个：**本技能的每个分数都要挂得住证据，并且留下可复查的落盘产物。** 判断规范不打折，取证只是把判断垫实。

## 三条不可让渡的规则

1. **判断先于取证。** 先想清楚推荐谁，再去取那几个人的证。不要先把脚本跑完再想推荐什么。
2. **分数必须有证据。** 每个维度至少引用一条 E1—E3 证据；只有 E4 的维度标「未核验」，不给数字。
3. **工具失败就降级，不中断、不编造。** `gh` 不可用时改用网页检索并标注来源；取不到的指标写「未核验」。

## 快速决策

1. 用户提到具体产品、项目或陌生名词：先执行「实体消歧」。
2. 用户已说明目的、约束和参考维度：直接检索，并明确你的理解。
3. 不同理解会显著改变结果：只问一个最关键的澄清问题。
4. 信息虽不完整但存在合理默认值：说明假设后继续，不要制造不必要的问答。

以下条件同时成立时，先澄清，不要先搜索、不要先建目录、不要先输出排行榜：

- 用户只给出宽泛方向，例如 `Agent memory`、RAG、AI workflow、observability。
- 用户说要「做产品/找项目」，但没有目标用户、核心场景、产品形态或必须能力。
- 该方向至少包含三个明显不同的产品赛道，选择不同赛道会改变首选仓库。

此时回答的形状是：一句话解释赛道为何分叉，然后只问一个带 2–4 个选项的问题，推荐选项放第一位。**用户回答前不要运行任何脚本。**

常见关键问题：

- 「你主要想直接使用、二次开发，还是研究它来做类似产品？」
- 「你说的相似，是界面形态、业务工作流，还是底层技术能力？」
- 「必须自托管和可商用吗？」

## 环境检查

进入取证前跑一次只读检查，只读状态，不安装、不登录、不修改配置：

```bash
python <skill-dir>/scripts/check_environment.py --capability discover --capability verify
```

`gh` 的版本与登录状态需要宿主执行最小只读探测（`gh --version`、`gh auth status`），把脱敏结果写成 probe JSON 后用 `--probe-results` 传入。格式与路由见 @references/setup-guide.md。

- `ready`：直接进入流程，不展示安装教程。
- `partial`：核心流程继续，只说明受影响功能与降级方式。
- `needs_setup`：只展示缺失项的配置步骤。
- `unavailable`：说明原因与恢复步骤，按降级矩阵继续。

检查未通过不阻塞澄清和画像；只影响取证手段。

## 工作流

`<skill-dir>` 是本文件所在目录。所有落盘产物在当前工作目录的 `./gh-research/{slug}/` 下。

### 1. 理解真实需求

从请求中提取：

- **行动目的**：直接使用、技术选型、二次开发、竞品研究、学习架构或自研产品。
- **目标对象**：产品类别、目标用户和典型使用场景。
- **核心能力**：没有这些能力就不应进入首选。
- **产品形态**：Web、桌面、CLI、SDK、Agent、工作流、画布或底层模型。
- **约束**：语言、技术栈、自托管、许可证、部署方式、维护成本。
- **质量偏好**：高 Star、近期增长、成熟稳定、活跃开发或企业采用。
- **排除项**：论文实现、资源合集、Demo、SDK、底层模型等是否与目标不符。

用户说「类似 X」时，不能仅搜索 X 的名字。

### 2. 实体消歧与产品画像

先搜索该名词或产品的准确含义。优先证据：官方网站与文档、官方 GitHub 组织与 README、可信发布公告。第三方文章只作补充。

确认：名称是否重名或缩写碰撞；用户指的是产品本体、开源仓库、API、插件还是生态项目；目标用户、核心工作流、交互形态、关键能力和部署模式。

形成一句「产品指纹」，例如：

> LibTV = 面向 AI 视频创作者的画布式工作台，覆盖剧本/分镜、图像与视频生成、素材编排，并可被 Agent/API 调用。

无法可靠确认实体时，向用户展示冲突的解释并请其选择。

### 3. 生成搜索简报并建库

整理简报：

```text
目标：
参考实体及产品指纹：
必须具备：
最好具备：
排除：
用户约束：
质量偏好：
```

如果无法填写「目标」或「必须具备」，且不同答案会改变推荐，先澄清。

简报确定后建库。`slug` 由**产品指纹**推导，不由用户原话推导——「想做 Agent memory 产品」和「找 memory API」是两个不同的库：

```bash
python <skill-dir>/scripts/gh_research.py init --slug <slug> --topic "<产品指纹>" --must "<必须能力,逗号分隔>" --exclude "<排除项>" --constraints "<用户约束>"
```

产出 `./gh-research/<slug>/brief.md` 与空的 `candidates.jsonl`。同一 slug 二次运行不会覆盖已有证据与分数。

### 4. 多路发现候选

至少覆盖三类查询，不依赖单个关键词：

- **实体与生态**：产品名、官方组织、替代品、竞品、集成和 Fork。
- **产品形态**：如 `infinite canvas`、`AI video workspace`、`code review agent`。
- **核心工作流**：如 `script to storyboard to video`、`webhook pull request review`。
- **技术能力**：如 MCP、GitHub App、self-hosted、multi-provider。
- **GitHub Topics 与中英文同义词**。

先宽搜发现词汇，再用高价值词收窄。每条查询记录它覆盖的意图维度：

```bash
python <skill-dir>/scripts/gh_research.py search --slug <slug> --query "<查询>" --intent "<覆盖的维度>" --limit 30
```

查询矩阵、停止条件与 `gh` 不可用时的替代路径见 @references/search-strategy.md。

`gh` 降级时，用网页检索得到候选后写入同一个库：

```bash
python <skill-dir>/scripts/gh_research.py search --slug <slug> --query "<查询>" --intent "<维度>" --from-json <候选JSON文件>
```

### 5. 核验候选

**取证范围由判断决定**：只对准备进入评分的候选取证，不要对搜到的全部仓库全量取证。

```bash
python <skill-dir>/scripts/gh_research.py verify --slug <slug> --repos owner/a owner/b
python <skill-dir>/scripts/gh_research.py readme --slug <slug> --repos owner/a owner/b
python <skill-dir>/scripts/gh_research.py code-search --slug <slug> --query "<核心能力的代码特征>" --capability "<对应的必须能力>"
```

必须核验：仓库链接、简介、当前 Star 与取证日期；是否归档、是否只是 Fork、主要语言、许可证；产品形态与核心能力是否真的匹配；最近提交、Release、Issue/PR、贡献者与文档状况；用户准备二次开发时的部署方式、配置复杂度、测试/CI 与许可证风险。

`code-search` 命中的 `file:line` 是 E1 代码级证据，是唯一能证实「真的具备该能力」的手段。只有 README 描述时只能记 E2，措辞停在「声明具备」。

近期 Star 趋势只有在获得可靠时间序列时才报告，并注明窗口与来源。没有可靠数据一律写「未核验」，不得用更新时间、总 Star 或主观感觉代替。

证据档位定义与取证要求见 @references/evidence-and-scoring.md。

### 6. 分开评分再排序

三个独立维度，均由你基于证据判断，脚本不替你打分：

- **相似度**：产品形态、核心工作流、核心能力、目标用户、部署模式与参考对象的接近程度。
- **适合度**：满足用户目的和硬约束、可复用架构、技术栈、许可证及落地成本。
- **项目质量**：同类采用度、维护活跃度、文档、发布与测试、贡献者健康度、许可证治理和可验证的 Star 趋势。

把分数与它引用的证据 id 一起写入：

```bash
python <skill-dir>/scripts/gh_research.py score --slug <slug> --from-json <评分JSON文件>
```

脚本会执行闸门校验：分数缺证据、引用 E4、引用不存在的证据 id、核心能力仅 E2 却给高相似度，一律拒绝写入并说明原因。校验通过后计算综合参考值与分级。

综合参考 = 相似度 45% + 适合度 35% + 项目质量 20%。用户明确强调某一维度时调整权重并说明。分级 A 85–100 / B 70–84 / C 55–69 / D <55。

评分锚点、权重细项与闸门规则见 @references/evidence-and-scoring.md。

### 7. 输出结果

```bash
python <skill-dir>/scripts/gh_research.py report --slug <slug>
```

产出 `report.md` 与自包含的 `report.html`，并在 stdout 返回两者的路径。

对话里先用 1–3 句话说明：你如何理解用户真实需求；对具体名词的消歧结果；结果中需要注意的类别差异。然后按 A、B、C 级组织候选，每个仓库至少包含链接、当前 Star、简介、分级、三维分数、**一条证据锚点**、推荐理由和注意事项。

**不要把候选库或全部证据 dump 进对话**——每个分数挂一条锚点即可，全量证据在 HTML 里。

最后给出：优先阅读顺序（通常 3 个以内，说明各自负责哪部分参考）、组合建议（产品层/工作流层/Agent 层/基础设施层如何取长补短）、数据说明（Star 获取日期、趋势来源、未核验项）。

**回答的最后一行给出 HTML 路径**，格式见 @references/report-format.md。文件未生成时不得给出路径，必须说明原因。

## 质量护栏

- 不把「高星但类型不同」的项目排在高度相似项目前面。
- 不把论文、模型、SDK、Awesome List 或底层引擎描述成完整产品。
- 不引用记忆中的 Star 数；实时核验后再写，并记录取证日期。
- 不因为描述中命中关键词就断言具备某项功能；只有 E1 证据才能说「具备」，E2 只能说「声明具备」。
- 核心能力仅有 E2 时相似度封顶 75，并在注意事项写明未验证实现。
- 不把近期提交、创建时间或 Release 数量称作 Star 趋势。
- 不隐瞒许可证、归档、项目过新、缺少源码或核心功能仅在云端等限制。已归档仓库不得进入 A/B 级。
- 不用过度精确的综合分掩盖证据不足；无法判断时明确标注未核验。
- 不让脚本失败中断整条流程，也不在失败后用推测补齐数据。
- 不用 HTML 报告替代对话输出，两者都要有。

## 示例

用户：「我想做一个类似 LibTV 的工具，希望找到相似度高且高星的项目。」

正确处理：先确认 LibTV 指向哪个产品并提炼产品指纹；判断目的为自研产品参考而非寻找底层文生视频模型；建库后分别搜索无限画布、AI 视频工作台、剧本到分镜/视频、Agent/API 调用层；对准备推荐的候选取证，用 code-search 证实画布与节点能力；相似产品放 A 级，高星短剧流水线放 B 级，ComfyUI 与画布 SDK 放 C 级或基础设施参考；Star 实时核验，趋势取不到写未核验；最后给出 HTML 路径。

错误处理：只搜 `LibTV` 或 `text-to-video`，按 Star 从高到低列出结果，分数没有证据，也不落盘。
